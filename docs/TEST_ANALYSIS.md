# Анализ результатов автотестирования

## Ответы на вопросы

### 1. Почему POST /api/v1/events - SKIPPED?

**Ответ:** Тест пропускается намеренно, потому что отправка событий уже полностью протестирована в тесте **T17.4** (`test_get_prompt_and_send_events`).

В тесте T17.4:
- Создаются event definitions для событий `user_signup` и `purchase_completed`
- Получается промпт через API и сохраняется `trace_id`
- Отправляются события через `POST /api/v1/events` с использованием `trace_id`
- Проверяется успешность отправки

Это сделано для избежания дублирования тестов и экономии времени выполнения. Код находится в строках **4016-4019** и **7978-8292** файла `auto-test.py`.

**Рекомендация:** Если нужно протестировать отправку событий в контексте External API теста, можно раскомментировать этот тест, но убедитесь что:
1. Созданы необходимые event definitions
2. Есть валидный `trace_id` от предыдущего запроса `/api/v1/get-prompt`

### 2. Ошибка 422 при создании конверсий

**Проблема:** При создании конверсий возвращается статус 422 (Unprocessable Entity) с ошибкой: `Field required: source_type`

**Причина:** API требует обязательное поле `source_type` со значением `'prompt_requests'` или `'event'`, но в коде создания конверсий это поле отсутствовало.

**Исправление:** ✅ **ИСПРАВЛЕНО**
- Добавлено поле `"source_type": "event"` в обе конверсии (строки ~7829 и ~7861)
- Конверсии используют события, поэтому используется `source_type: "event"`
- Если бы использовались промпты, нужно было бы `source_type: "prompt_requests"` и `source_prompt_id`

**Детали API:**
- `source_type: "event"` требует `source_event_name`
- `source_type: "prompt_requests"` требует `source_prompt_id`
- Поле `source_type` обязательно согласно схеме `ConversionFunnelCreate`

**Результат:** Теперь конверсии должны создаваться успешно.

### 3. Воронка 'Purchase Funnel' не найдена на UI

**Проблема:** Воронка создается через API, но не отображается на UI сразу.

**Причина:** 
- UI может не обновляться мгновенно после создания через API
- Данные воронки могут не отображаться, пока не будет достаточно событий
- Поиск воронки на UI был слишком простым (только проверка наличия текста в HTML)

**Текущее поведение:** Код уже имеет fallback механизм:
- Если воронка не найдена на UI, проверяется через API
- Если воронка найдена через API, тест считается успешным

**Исправление:** ✅ **УЛУЧШЕНО**
- Добавлено явное обновление страницы перед поиском воронки (строка ~8453)
- Улучшен поиск воронки на UI:
  - Добавлен поиск по видимым текстовым элементам
  - Проверяется видимость элементов перед проверкой содержимого страницы

**Результат:** Страница обновляется перед поиском, что должно помочь найти воронку на UI. Если не найдена - проверка через API все равно работает.

### 4. UI кнопка Start не найдена - overlay перехватывает клики

**Проблема:** Overlay (модальное окно с классом `bg-black/80`) перехватывает pointer events, не позволяя кликнуть на кнопку Start. Overlay не закрывается автоматически.

**Причина:** После создания A/B теста может открываться модальное окно или диалог, который блокирует взаимодействие с элементами под ним.

**Исправление:** ✅ **ЗНАЧИТЕЛЬНО УЛУЧШЕНО** (строки ~8686-8720)
Добавлена многоуровневая обработка overlay:

1. **Обнаружение overlay:** Проверяются различные селекторы overlay/modal
2. **Ожидание закрытия:** Ожидается автоматическое закрытие overlay (до 5 секунд)
3. **Множественные стратегии закрытия:**
   - **Способ 1:** Нажатие клавиши Escape
   - **Способ 2:** Поиск и клик по кнопке закрытия (различные селекторы)
   - **Способ 3:** Клик вне модального окна (в центр overlay)
   - Проверка что overlay действительно закрылся
4. **Множественные стратегии клика:**
   - Обычный клик (с таймаутом 10 секунд)
   - Force click (если обычный не работает)
   - Fallback на API (если UI клик не удался)

**Результат:** Теперь overlay должен закрываться более надежно. Логи покажут какой способ сработал.

**Результат:** Тест T19.1 теперь должен получать refresh token и успешно проходить.
